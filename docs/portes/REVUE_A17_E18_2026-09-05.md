### B-2 · `depot.ts:547` et `:566` — la relecture d'après coup n'est pas protégée : le 409 promis redevient un 500

    const existante = siren === null ? null : await lireFicheParSiren(siren);                   // :547
    const existante = externalRef === null ? null : await lireFicheParRefExterne(externalRef);  // :566

Ces deux `await` ne sont pas dans un `try`. Le code traite le cas « la lecture **ne trouve rien** »
(`existante === null` → message générique, pas de `details`) ; il ne traite **pas** le cas « la
lecture **échoue** ». Une rejection remonte hors de `traduireEchecDeContrainte`, sort de
`mettreAJourEntreprise`, sort de la transaction, et arrive au gestionnaire d'erreurs qui rend
`INTERNAL_ERROR` (`apps/api/src/erreurs.ts:250-251`).

**Le chemin est atteignable, et il n'est pas exotique.** `modifierUneEntreprise`
(`domaines/companies/service.ts:340`) exécute l'`UPDATE` **dans** `db.transaction(...)`. Le `catch`
demande alors une **seconde** connexion au pool — `lireFicheParSiren` interroge le `db` global et non
`tx`, et c'est d'ailleurs pour cela que le mécanisme fonctionne : la connexion de la transaction est
en état avorté — **tout en tenant encore** celle de la transaction. Le pool est dimensionné
`max: 10`, `connectionTimeoutMillis: 5_000` (`apps/api/src/db.ts:22-28`). Dix `PATCH` conflictuels
simultanés tiennent les dix connexions, les dix relectures attendent une onzième, expirent à 5 s — et
les dix **409 deviennent dix 500**, après cinq secondes chacun. Cette dépendance au dimensionnement
du pool n'est écrite nulle part dans le module.

  (« **garantis** : le statut 409 et `error.code` — décidés par la contrainte, **sans aucune

  « le chemin dégradé est un **contrat** — statut et `code` garantis, `details` au mieux ». Le
