## 4. LE POINT DUR — deux membres du critère P-B n'ont pas d'objet, et il faut le dire avant de signer

Le critère spécial de P-B (09 §62) a **trois** membres. Le premier — l'accès financier croisé — est
prouvé (§3, critère 3). Les deux autres ne le sont pas, **et la cause est structurelle**.

### 4.1 « Un consultant ne voit pas les missions d'autrui »

La politique de route `type: 'mission'` **existe** et fonctionne. Mais elle **ne fait pas ce que le
critère demande**, et son propre code le dit sans ambiguïté (`politique.ts`, en-tête) :

> _« La politique de route dit QUI ENTRE, pas CE QUE LE SQL RAMÈNE. L'isolation "un consultant ne
> voit pas les missions d'autrui" est portée par le DÉPÔT (jointure obligatoire sur `mission_users`),
> pas par ce crochet. Deux garde-fous, deux natures ; confondre les deux, c'est croire qu'une porte
> fermée trie le courrier. »_

Et le test du banc l'écrit à son tour, en refusant le piège : un consultant appelant
`/essai/missions/<uuid quelconque>` reçoit **200**, avec ce commentaire — _« Ces politiques
garantissent l'identité, PAS la propriété de la ligne. Un test qui attendrait 403 ici confondrait les
deux garde-fous. »_

**Mesuré : `mission_users` n'apparaît dans AUCUN code de production.** Sept occurrences dans le
dépôt, **toutes en commentaire**. Il n'existe ni route missions, ni dépôt missions — c'est L3.

> **Conclusion, et elle est désagréable : le critère 2 ne peut pas être coché, et il ne peut pas non
> plus être refusé. Il n'a pas d'objet.** Le cocher serait exactement le défaut que ce dépôt poursuit
> depuis trois jours — **une mesure vraie sur ce qu'elle observe, qui répond à une autre question que
> celle posée**. La porte cocherait « le consultant ne voit pas les missions d'autrui » sur la foi
> d'un garde qui, de son propre aveu écrit, ne regarde pas les missions.

### 4.2 « Push sur la session d'un autre auditeur → `forbidden` »

Même forme, même cause. `type: 'proprietaire_session'` **vérifie l'identité, pas la propriété** ; la
propriété de session du 05 §9.9 vit dans le **service de sync**, qui est **L6**. La table
`sync_sessions` **n'existe pas** dans les migrations (`sync_log` existe, c'est autre chose), et il n'y
a **aucune route de push**. Rien à traverser, donc rien à refuser.

### 4.3 Une conséquence à ne pas laisser passer : le balayage sentinelle est **pré-désarmé** pour L3

Le balayage cartographie trois paramètres : `id` → un cadrage **réellement semé** ; `missionId` et
`sessionId` → **deux UUID littéraux semés nulle part**. C'est légitime aujourd'hui, parce que ces deux
noms ne servent qu'aux bancs d'essai, qui ne lisent aucune ligne.

**Mais l'en-tête du module promet exactement le contraire pour demain** — _« la route
`/v1/missions/:id/interview-plan` ajoutée demain oblige son auteur à semer une mission réelle, sans
quoi le balayage rougit »_. Or le jour où L3 ajoute une route de produit portant `:missionId`, le
paramètre sera **déjà cartographié** vers une ligne inexistante : `parametresNonCartographies` restera
vide, la route rendra 404, elle sera comptée « non exercée », et `couverture.exerces > 0` restera
satisfait **par la seule route de cadrage**. Le balayage serait vert sur une route qu'il n'a jamais
traversée — **le défaut que son propre en-tête dit refuser de reproduire**.

**Ce n'est pas un défaut d'aujourd'hui, c'est une amorce datée.** Elle se ferme en retirant
`missionId` et `sessionId` de la cartographie le jour où une route de produit les porte, pour que le
garde exige une ligne réelle. **À porter au brief de L3**, pas à corriger ici : aujourd'hui le
retirer rendrait le balayage rouge sur les bancs, ce qui serait un garde qui crie à tort.

## 5. Ce que le lot a livré EN PLUS, et qui n'est dans aucun critère

Le gardien A02 doit lire dans les **deux sens** (09 §3-6). Sens code → exigences, trois éléments :

- **`lireUtilisateur` (`users/depot.ts:170`) est DU CODE MORT** — zéro appelant dans tout le dépôt.
  Écrit pour un `GET /v1/users/:id` **jamais câblé** : le CRUD a une liste et pas de lecture unitaire.
  **C'est du code orphelin au sens du §6 : soit la route manquante est câblée, soit la fonction est
  supprimée.** Relevé par l'agent croisé, pas par l'auteur.
- **`PATCH /v1/users/:id` pose `usageProfile: 'expert'` sur un compte NON habilité**, alors que
  03 §19.1 décrit le mode expert comme celui d'un auditeur habilité. **Épinglé sans être tranché**,
  ce qui est le bon geste : c'est une question de spec, elle va en `DECISIONS.md` avant la porte.
- **Cinq `throw incoherenceInterne()` inatteignables dans `users/service.ts`** (L211, L262, L317,
  L363, L456). Ils se déclenchent quand une écriture du dépôt rend `null` ; or la frontière du service
  est déjà scellée en amont par `avant === null → NOT_FOUND`. **La moitié « dépôt » est prouvée, la
  moitié « service » reste scellée — et c'est celle qui peut régresser.** Question de conception, pas
  trou de test.
