## 2. TRADUCTION CONCRÈTE DANS CLAUDE CODE (comment ça se pilote réellement)

- **Le dépôt** contient : le pack (dossier `/docs`, les 12 fichiers), un `CLAUDE.md` racine qui impose les 8 invariants + les interdictions du contrat technique (fichier 11 §2 et §8) + le pipeline §3 + « lis le fichier 11 puis les fichiers du pack indiqués par l'ordre de lecture du 00_INDEX avant chaque lot », et les définitions de sous-agents (`.claude/agents/`) correspondant aux rôles ci-dessus (un fichier par gabarit : reviseur-backend, testeur-e2e-offline, gardien-spec, securite, etc.).
- **(V2.12) Une session Claude Code = un INCRÉMENT** (découpage du fichier 11 §6 ; pour les petits lots, l'incrément EST le lot), lancée en autopilote avec le brief du lot (**fichier 07 V2.2** : contenu + critères d'acceptation). La raison est la COUPURE : un lot de 8 jours dans une seule session finit par épuiser le contexte — la session qui se termine PROPREMENT (11 §9ter : ETAT.md + commit + push) ne perd jamais rien, celle qui meurt en plein vol perdait tout ce qui n'était pas écrit. L'orchestrateur (la session principale) DÉLÈGUE aux sous-agents : implémentation → puis il invoque explicitement le réviseur croisé, les testeurs, le gardien de la spec — chaque rôle rend son rapport dans la session. **Dès que le contexte se tend, l'orchestrateur clôt la session proprement plutôt que de la pousser à la limite.**
- **Les tests sont des hooks bloquants** : la CI refuse le merge si un test échoue ; les 8 scénarios offline, les tests RBAC/propriété et le diff schéma-vs-04 sont marqués `@critique` et ne peuvent jamais être skippés.
- **Williams n'intervient qu'aux portes** (§4) : fin de lot = démo + checklist — 15 minutes de validation humaine, pas de micro-management. Tout le reste est autopiloté.

## 3. LE PIPELINE — 7 ÉTAPES OBLIGATOIRES PAR LOT (aucun raccourci)

1. **Brief** — l'orchestrateur charge l'ordre de lecture du lot (00_INDEX) + le contenu et les critères du lot (fichier 07 V2.2) ; le gardien confirme le périmètre.
   1bis. **Conception (V2.11 — lots à risque UNIQUEMENT : L2, L3, L5, L6)** — le chef d'équipe rédige une note `docs/conception/LOT_<X>.md` ≤ 1 page : découpage, interfaces exposées, points durs, plan de tests — validée par A01 + gardien AVANT la première ligne de code. Une heure de conception épargne un jour de refactor sur le cœur critique ; les lots simples (L0, L1, L4, L7) sautent cette étape.
2. **Implémentation** — l'équipe concernée code, en TDD sur les parties critiques (sync, RBAC, scoring, machine à états : tests écrits AVANT).
3. **Auto-revue** — l'agent qui a codé relit son diff contre les invariants (checklist automatisée : pas de couleur en dur, pas de référence client, UUID client sur les entités offline, requêtes filtrées par mission, écriture réservée au propriétaire de session…).
4. **Revue croisée** — le réviseur de l'équipe (qui n'a rien produit) relit TOUT ; désaccord → arbitrage A01, tracé dans DECISIONS.md.
5. **Tests automatisés** — unitaires + intégration + E2E du lot + NON-RÉGRESSION de tous les lots précédents (la suite complète tourne à chaque fois).
6. **Contrôle d'acceptation** — le gardien (A02) coche un par un les critères du lot ET met à jour la matrice de traçabilité (E1-E47 — V2.9), **dans les DEUX sens (V2.11)** : exigences → code (rien d'oublié) ET code → exigences (**toute route, table, écran ou job livré se rattache à une exigence E1-E47 OU à une fiche AMELIORATIONS.md §5.9 — le code orphelin est REFUSÉ** ; généralisation du 11 §8.6) ; la sécurité (A51) et l'UX novice (A54) rendent leur verdict quand le lot les concerne ; la **Definition of Done transverse** (ci-dessous) est cochée intégralement.
7. **Porte humaine** — démo à Williams (staging), checklist de fin de lot signée, merge en principal, tag de version, changelog.

**DEFINITION OF DONE TRANSVERSE (V2.11 — s'ajoute aux critères propres de chaque lot, cochée par le gardien à l'étape 6)** : lint + typecheck stricts = 0 erreur · tous les tests verts, AUCUN test skippé (§5.7) · **couverture ≥ 90 % sur les modules critiques** (moteur de sync, crypto locale, scoring, RBAC/propriété — mesurée, pas déclarée) · migrations up/down exécutées sur staging · tout écran livré avec ses 4 états (§33.2) · axe-core vert · scénario fil rouge `@filrouge` (§4) vert · README de l'app à jour · aucun TODO/FIXME sans entrée DECISIONS.md ou AMELIORATIONS.md · diff schéma-vs-04 = zéro écart.

### 4bis. LE FIL ROUGE CUMULATIF (V2.11 — l'intégration inter-lots ne se découvre plus en semaine 4)

Deux missions canoniques vivent en FIXTURES de test dès L1 et GRANDISSENT à chaque lot : **FIL-TPE** (micro fictive, 8 personnes, 1 entretien, ~30 questions) et **FIL-GC** (grand compte fictif : arbre 150 unités sur 4 niveaux, 60 sessions planifiées, ~8 000 réponses générées par script — le générateur est un outillage de test du L1). Un test Playwright unique marqué **`@filrouge`** rejoue à CHAQUE merge le parcours de bout en bout DISPONIBLE À DATE : création mission → import arbre → questionnaire figé (L3) → import banque de recette (L4) → session hors ligne, cotation, à-revoir, photo (L5) → sync + rejeu idempotent (L6) → export §36.3 (L7) — chaque lot ne fait qu'ALLONGER le scénario, jamais le réécrire. Toute porte exige `@filrouge` vert sur LES DEUX missions. C'est aussi la preuve continue du « de la TPE au grand groupe » : la même app, le même parcours, aux deux échelles.

**Porte échouée (V2.11 — le principe « les portes arrêtent » a désormais sa procédure)** : verdict ÉCHEC tracé dans le fichier de porte (11 §9bis) avec la liste des critères non tenus → SEULS les correctifs de ces critères sont autorisés (aucun lot suivant ne s'ouvre, aucun périmètre ajouté) → la porte se rejoue EN ENTIER (jamais « les 3 points qui manquaient ») → deux échecs consécutifs de la même porte = arbitrage Williams type P-DESCOPE (réduire, jamais bâcler).

## 5. RÈGLES D'AUTOPILOTAGE (garde-fous du mode autonome)

1. Un agent qui a un doute d'interprétation de la spec NE DEVINE PAS : il pose la question dans DECISIONS.md, l'orchestrateur tranche par la règle de précédence (§32-36 (corrections et compléments V2.2→V2.12 — le plus récent prévaut) > §24-31 > §16-22 > §1-15) et remonte à Williams si c'est un choix produit.
2. Tout écart à la spec est soit refusé, soit documenté comme amendement horodaté — jamais silencieux.
3. Jamais deux lots en parallèle sur les mêmes fichiers ; le moteur de sync (L6) se développe SEUL, rien d'autre en parallèle cette semaine-là.
4. Chaque fin de journée d'autopilote : commit + push + **mise à jour de `docs/ETAT.md` (11 §9ter — V2.12)** + état des tests + résumé de 10 lignes dans le journal **+ une ligne de burn-down (V2.11) : consommé / restant par lot vs la référence 26 j-h — c'est ce qui rend la porte P-DESCOPE FACTUELLE au 15/09, pas une impression**. Williams lit 2 minutes, réoriente si besoin.
5. Budget d'itération : si un même bug résiste à 3 tentatives autopilotées, arrêt et escalade humaine (anti-boucle infinie).
6. Le code de test n'est jamais écrit par l'agent qui a écrit le code testé (croisement systématique producteur/vérificateur).
7. Interdiction de « simplifier temporairement » la sécurité ou la sync pour faire passer un test — la CI détecte les tests désactivés.
8. **Budget de contexte (V2.2)** : chaque sous-agent ne charge QUE les sections listées par l'ordre de lecture de son lot ; interdiction de charger le pack entier dans un sous-agent.
9. **CANAL D'AMÉLIORATION (V2.11 — autorisation explicite de Williams : si l'implémentation révèle un manque pour que l'outil soit extrêmement professionnel, l'autopilote PEUT l'ajouter — dans CE cadre, jamais en dehors)** :
   - **Étage 1 — micro-améliorations, autorisées D'OFFICE** : confort et robustesse évidents (libellé plus clair, état vide manquant, tri par défaut, message d'erreur, raccourci, focus) qui ne touchent NI le schéma 04, NI l'API, NI la crypto, NI le périmètre fonctionnel — plafond 0,5 j cumulé par lot, chaque ajout = une ligne dans `AMELIORATIONS.md` (append-only, même format que DECISIONS.md), relu par le réviseur croisé comme le reste du code.
   - **Étage 2 — fonctionnalités manquantes, PROPOSÉES puis arbitrées** : toute vraie fonctionnalité absente de la spec = fiche `AMELIORATIONS.md` (constat terrain, valeur pour l'auditeur, coût estimé, impact schéma/API) — **JAMAIS implémentée avant arbitrage**. Arbitrage à la porte suivante par Williams : ABSORBÉE (budget pris sur la marge, 2 j max en Phase 1), PHASE 2 (le défaut), ou REFUSÉE. Le fichier 04 reste inviolable hors de la révision de spec de P-D (11 §8 inchangé).
   - Le gardien A02 vérifie à chaque étape 6 que tout code non tracé E1-E47 a sa ligne AMELIORATIONS — l'autorisation d'améliorer n'est jamais une porte au scope creep silencieux : elle a un registre, un plafond et un arbitre.
